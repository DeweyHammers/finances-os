# Finances OS — Claude Code Project Guide

## Stack

- **Nextron** (Electron + Next.js 14, `app/` router, static export)
- **SQLite** through the **shared data layer** `shared/data/` (libsql backend — a local file, or an embedded replica of the user's own Turso database once sync is on; no Prisma client at runtime since Oct 2026). `prisma/schema.prisma` is still the schema's source of truth, dev DB at `prisma/dev.db` — see "Shared data layer"
- **Refine.dev** (`@refinedev/core`) for data operations (`useList`, `useOne`, `useCreate`, `useUpdate`, `useDelete`)
- **MUI v9** (`@mui/material`, `@mui/icons-material`) — all components use `slots`/`slotProps`, NOT `component`/`sx` overrides on deprecated APIs
- **Vitest** for unit tests

## Commands

```
npm run dev          # Start Nextron dev server (hot-reload renderer)
npm run build        # Build → dist/win-unpacked (then an NSIS installer, which Smart App Control blocks here); passes --publish never
npm run deploy:prod  # Ship the current code to the INSTALLED app on this PC (asar swap) — see "PROD Deployment Flow"
npm run test         # Run Vitest test suite
npm run db:push      # Copy prisma/dev.db → %APPDATA%\finances-os\database.db (PROD)
npm run db:pull      # Copy PROD → dev.db
npx tsx scripts/generate-schema-sql.ts                  # After a schema.prisma change: regenerate shared/data/schema.sql (+ edit MODELS, bump SCHEMA_VERSION, add the step in shared/data/migrations.ts) — see "Schema changes"
npx prisma db push --skip-generate --accept-data-loss   # Optional: apply the schema to dev.db with Prisma (the app's own migration does it on the next start anyway)
npx prisma generate  # Only for the Prisma-client scripts (prisma/seed.ts, scripts/balance-bills.cjs); the app itself no longer loads it
```

- **`nextron.config.js` → `startupDelay: 60000`** is required. Nextron 10 turns it into `retries = startupDelay / 500` for its renderer port check; the default 0 makes `npm run dev` fail instantly ("Failed to start renderer process with port 8888 in 0ms") and orphan `next dev` on port 8888.
- **Every `git push` runs the full test suite first** (`.githooks/pre-push`, enabled by the `prepare` script → `git config core.hooksPath .githooks`; fresh clones get it on `npm install`). It runs with `CI=true`, so missing snapshots fail instead of being written. A failing test cancels the push. Emergency bypass: `git push --no-verify`. `.gitattributes` keeps the hook LF-only, since a CRLF `#!/bin/sh` breaks it. Typecheck isn't gated yet (12 known test-file errors).
- **GitHub Actions (`.github/workflows/test.yml`) runs the same suite once per commit** (pull requests + pushes to main) on a hosted Windows runner, and that runner is slow and starved compared to the dev PC: on Oct 30 2026 three unrelated `beforeEach` hooks timed out at 10 s in the same moment, and in a later run the `sync.routes.test.ts` worker died mid-file with no JS error (native libsql under load) — each time the twin run of the same commit, and every local run, passed. A third run then sat for 18 minutes with the worker's JS thread blocked inside a native libsql sync call (no Vitest timeout can fire then), in the same file right after a conflict re-bootstrap — most likely a second native sync entered while the first, timed out on the slow runner, still held libsql's sync lock; `backends/libsql.ts → sync()` now joins a sync still in flight instead of starting another (close() always did), though the hang could not be reproduced locally (a sync against the mock finishes in < 30 ms). So `vitest.config.ts` gives hooks 60 s / tests 30 s under `CI` and runs files one at a time under `GITHUB_ACTIONS` (not `CI`: the pre-push hook sets that too and should stay fast), and the workflow runs the suite as two steps — everything else (12 min cap) and `sync.routes.test.ts` alone (6 min cap) — each retried once on failure, a cancelled hang included. A real failure still fails twice and turns the check red; the pre-push hook is the gate that matters.
- **`dev` passes `--remote-debugging-port=9222`** on purpose. Nextron otherwise appends `--remote-debugging-port=5858` — the API server's port. Chromium DevTools then grabs `127.0.0.1:5858`, and since the API binds loopback only (`main/api-server.ts` → "Network exposure"), the API either fails to start or the renderer's fetches hit DevTools. VS Code's `nextron:renderer` attach config uses 9222 to match.
- **After a schema change, restart the dev app** — the main process reads `shared/data/schema.ts` at startup. (`prisma generate` used to fail with `EPERM … query_engine-windows.dll.node` while the app ran because it held the engine DLL; the app no longer loads Prisma, so that is gone.)
- **Schema changes ship as migrations, not `db:push` (since Nov 10 2026).** The installed app reads a synced copy of the user's cloud database (`replica.db`), so copying dev.db over `database.db` no longer reaches it — and the cloud has no file to copy onto. A schema change = edit `prisma/schema.prisma` (new columns LAST in their model, nullable or defaulted) → `MODELS` in `shared/data/schema.ts` → bump `SCHEMA_VERSION` → add a frozen, idempotent step to `shared/data/migrations.ts` → `npx tsx scripts/generate-schema-sql.ts` → save the previous `schema.sql` as `shared/data/test-fixtures/schema-v<N>.sql` and extend `migrations.test.ts`. The new bundle (`npm run deploy:prod`) then migrates its database on first use and the next sync pushes the new shape to the cloud. See "Shared data layer" → `migrations.ts`. `db:push` still copies DATA for a local-only install.
- **The installer ships an EMPTY database, never dev.db.** `npm run build` first runs `prebuild` → `scripts/build-template-db.mjs`, which rebuilds `prisma/template.db` from the schema with zero rows and refuses to continue otherwise; `electron-builder.yml` packages that file and `shared/prisma.ts` copies it to `%APPDATA%` on a fresh install only. Until Oct 24 2026 the build bundled `prisma/dev.db` (real bills and transactions) — an installer built before that must not be shared. Existing installs are unaffected (their `database.db` already exists).

## PROD Deployment Flow

1. Verify all changes in dev mode (`npm run dev`)
2. **Bump the version** — `npm version X.Y.Z --no-git-tag-version` (updates package.json + package-lock.json), in the same commit as the change: patch for a fix or tweak, minor for new behaviour, below 1.0 while alpha. User rule since Nov 6 2026, when two different bundles went out as 0.4.0 the same evening and neither Settings nor the `app.asar.<version>.<stamp>.bak` backups could tell them apart; 0.5.0 was the first bump under it. `deploy:prod` prints "Installed app.asar <old> → <new>" — those two numbers should never be equal.
3. Only when user explicitly says to push: `npm run db:push` (copies dev.db to PROD's local file — data only; a synced install reads `replica.db`, and schema changes travel as migrations, see Commands)
4. Then `npm run deploy:prod` (ships the code to the installed app — required for UI/code changes to take effect)

**NEVER run `npm run db:push` without explicit user instruction.** DEV is for experimentation; PROD changes are deliberate.

**No installers, Releases or in-app updates (since Oct 30 2026).** SignPath Foundation declined the free code-signing application, and Windows Smart App Control on the dev PC blocks every unsigned installer: electron-builder's NSIS stub during `npm run build` (`spawn UNKNOWN` in `computeScriptAndSignUninstaller`, Code Integrity event 3077), a Setup exe downloaded from a browser ("we could not verify its publisher", no "run anyway"), and electron-updater's silent install. Paying for a certificate makes no sense while nobody else uses the app, so (user decision, Oct 30 2026): every GitHub Release, tag and installer artifact was deleted; `electron-updater`, `main/updates.ts`, `main/updater.ts` and `main/smart-app-control.ts` were removed (see "Updates — removed"); `electron-builder.yml` has no `publish` block; the version was reset to **0.4.0** (alpha — Settings → General shows "Alpha ·" in the Version row while the version is below 1.0, `isAlpha` in `SettingsPage.tsx`); and `.github/workflows/test.yml` only runs the test suite on pushes and PRs. Don't try to turn Smart App Control off from here — it's one-way on Windows 11 and the user's call.

**`npm run deploy:prod` (`scripts/deploy-prod.mjs`) is how code reaches PROD.** The installed app (`%LOCALAPPDATA%\Programs\Finances OS`) is updated in place by swapping ONLY its JavaScript bundle (`resources/app.asar`) — no new executable or DLL is loaded, so nothing trips Code Integrity. The script builds `dist/win-unpacked` (`build-template-db.mjs` → `nextron build --no-pack` → `electron-builder --dir --publish never` with `ELECTRON_BUILDER_ALLOW_UNRESOLVED_DEPENDENCIES=true`; `--skip-build` reuses the last one), then verifies: the new asar's `package.json` version matches the repo's; every entry of `dependencies` is inside the asar (a stale node_modules once built one WITHOUT a dependency and the app crashed on launch — `npm ci` fixes that); every file under `app.asar.unpacked` is sha256-identical to the installed one (only `prisma/template.db` may differ); and `Finances OS.exe` is the same Electron build (same length, and only the few bytes of the asar-integrity resource electron-builder stamps into the exe may differ — 69 on Oct 30 2026). Any other difference STOPS it — this path can't ship binaries, so a new Electron or libsql needs a real installer. `--check` ends there. Otherwise it refuses while the app is running, backs up the installed asar to `app.asar.<old version>.bak`, copies the new one, launches the app and waits for `GET /api/meta` to report the new version. The database is never touched. The same steps were done by hand on Oct 29 2026 (1.3.0 → 1.3.2, then the local-first bundle) before they became the script.

## Sandbox mode (Oct 2026)

"Try a sandbox" (Overview toolbar, left of Optimize) lets the user experiment on a COPY of the database and then throw it away or keep it. `main/sandbox.ts` owns it; `shared/db.ts` makes it possible.

- **`getStore()` (shared/db.ts) is the swappable connection.** `switchDatabase(url, beforeConnect?)` closes the current store's file, runs the file operation while nothing holds either file, then creates the next store (the libsql backend opens its file lazily, on the first query). Routes call `getStore()` on every request — never cache the store in a module variable. The libsql close quirk that makes this work is described under "Shared data layer".
- **Files.** The copy is `sandbox.db` beside the real file (`prisma/sandbox.db` in dev, `%APPDATA%\finances-os\sandbox.db` in PROD; both gitignored by `*.db`). `enter` copies real → sandbox and switches; `discard` switches back and deletes the copy; `keep` writes `database.db.<stamp>.bak` (same naming as `db-sync.cjs`), overwrites the real file with the copy, switches back, deletes the copy. A sandbox never survives a restart: `cleanupStaleSandbox()` runs before the API starts and deletes any leftover copy, so the app always opens on real data.
- **Routes.** `GET /api/sandbox` → `{ active, enteredAt, transactionsAdded }`; `POST /api/sandbox/{enter|discard|keep}`. Wrong-state calls (enter twice, discard when inactive) are `409` via `SandboxError`. Registered BEFORE the generic `/api/:resource` routes.
- **Renderer.** `SandboxProvider` (app/providers.tsx) fetches the status once; `SandboxBanner` is the sticky amber strip above every page while active, with confirmed Discard (shows how many transactions were recorded in the sandbox — those are what Discard loses) and Keep; `SandboxButton` is the entry point (renders nothing while a sandbox is active). It lives in **Settings → Data** since Oct 27 2026 (it sat in the Overview toolbar before; the user moved the rarely-used controls out of that toolbar, together with the surplus target editor — see "Settings page"). Every action **reloads the window** on purpose: Refine's query cache, page state and the Overview's stale-alert check all have to restart against the other file. The raw fetches live in `lib/sandbox-api.ts`; `lib/api-url.ts` holds the shared `API_URL`.
- **Tests.** `main/api-server.routes.test.ts` → `sandbox (/api/sandbox)` covers enter/discard/keep against the temp test DB (the copy lands in the temp dir, never near dev.db).

## Shared data layer (Oct 27 2026) — `shared/data/`

Phase A step 1 of `plans/phone-app-and-sync.md`: every read and write goes through ONE data layer that needs nothing but `exec(sql, params) → rows` from its backend, so the desktop (Electron main) and, later, the Android app run the same code against the same rules. The Express routes in `main/api-server.ts` are thin HTTP wrappers over it; `main/api-server.routes.test.ts` is the contract that pins its behaviour (unchanged by the switch).

- **Files.** `sql.ts` the `SqlExecutor` interface (+ `splitStatements`); `schema.ts` the typed model metadata (`MODELS`: columns in Prisma order, scalar type, nullability, `cuid`/`now` generated defaults; `resolveModel()` = the old case-insensitive `getModel`), `SCHEMA_VERSION`; `schema.sql` + `schema-sql.ts` the GENERATED DDL (never edit — `npx tsx scripts/generate-schema-sql.ts` after every `schema.prisma` change; `schema.test.ts` fails when either is stale or `MODELS` disagrees with the DDL); `coerce.ts` `transformBody` (moved from the API, applied inside the store) + strict value validation; `store.ts` the `DataStore`; `backends/libsql.ts` the desktop backend; `migrations.ts` the steps that bring an older database up to `SCHEMA_VERSION`; `cuid.ts`, `errors.ts`.
- **`shared/db.ts`** resolves the real database path (dev.db / `%APPDATA%` / `FINANCES_OS_TEST_DB_URL`), owns the swappable store (`getStore()`, `switchDatabase`) and exports a tiny `prisma` object (`$queryRawUnsafe`, `$executeRawUnsafe`, `$disconnect`) ONLY so the route tests run unchanged. `shared/prisma.ts` is a re-export of it.
- **Behaviour = the old Prisma routes, deliberately.** Lists: `?field=value` equality, `?field_like=` contains (LIKE, wildcards escaped), `_sort`/`_order` (`asc|desc`, several fields), total count; `_start`/`_end`/`q` ignored. Create ignores a client `id` and the legacy `client`/`contracts` keys, generates a cuid, fills `now()`, leaves literal defaults to the DDL. Update: URL id wins; a missing row throws (`NOT_FOUND` → 500) except `AppSettings/global`, which is created on first save. Validation is Prisma-strict (`"5"` for an Int, an unknown column, a null in a NOT NULL column → `VALIDATION` → 500); `transformBody` still coerces the known numeric keys first. **`POST /api/batch { operations: [{ op: create|update|delete, resource, id?, values? }] }` → `{ results }`** (Nov 6 2026) runs many writes as ONE transaction (`DataStore.batch`; all or nothing; registered after the write gate and before `/api/:resource`; `express.json` limit raised to 16 mb for it) — Optimize's whole plan goes through it, and anything else that writes many rows should too. The rules live in the store now (`applyCreate` / `applyUpdate` / `applyRemove`, shared by the single calls and `batch`): Income single-primary (create/update demote the others; a patch WITHOUT `isPrimary` clears it — historic quirk kept), BudgetCategoryItem delete snapshots the name onto `AccountTransaction.categoryName` first. All in one serialised lock; the rules run in BEGIN/COMMIT.
- **Storage is what the Prisma client wrote**, so dev.db / PROD are used in place and Prisma tools still read them: Boolean → 0/1, DateTime → Unix **milliseconds** (reads also accept the ISO text older rows hold and SQLite's `CURRENT_TIMESTAMP` text), cuid v1-shaped ids. Verified Oct 27 2026 against dev.db: all 1510 rows of every model read byte-identically through the old Prisma client and the new API, and rows the API writes read back identically through Prisma.
- **`SchemaVersion`** (`version`, `appliedAt`; a Prisma model too, so `db push` keeps it) — `createDatabase(exec)` applies `schema.sql` to an empty file (template.db, demo.db and the test DB are built from the same statements by `scripts/empty-db.mjs`), `prepareDatabase` runs on a store's first use (empty file → full schema; anything else → `ensureSchemaVersion`). `SCHEMA_VERSION` is **3** since Nov 12 2026 (1 = the Prisma-era shape; 2 = `Income.baseHours` / `baseTaxes` / `baseFlatDeductions` + the `IncomeOverride` table; 3 = `Income.workWeekStart` + the `BillNoCharge` table, 0.7.0 — `test-fixtures/schema-v2.sql` is the frozen version-2 shape). An app OLDER than its database refuses to write (the schema gate, `schemaVersionGate`).
- **`migrations.ts` (Nov 10 2026) — the first real migration.** `ensureSchemaVersion` runs `migrationStatements(db)` + the version stamp in ONE transaction on a store's first use (all or nothing; a failure leaves the file at its old version and the next first use retries). The steps are FROZEN SQL (never derived from the current `schema.sql`), idempotent (they read `sqlite_master` and emit only what is missing — dev.db may already have the shape from `prisma db push`), and use no PRAGMA so the same function runs against the cloud. On a synced copy the DDL is an ordinary local write that the next sync pushes — that is how the user's Turso database gets a new shape; nothing is copied. `main/sync.ts → replaceRemote` runs the same statements over Hrana before loading a whole dump into a cloud that still has the old shape (Sandbox Keep, Import, "keep this PC's changes", first upload). `dumpDatabase` reads `SELECT *` and picks this build's columns by name, so a source made by an older build dumps with the new columns NULL instead of failing. Pinned by `shared/data/migrations.test.ts` (a version-1 database from `test-fixtures/schema-v1.sql` ends up column-for-column identical to a fresh one, rows untouched, idempotent, rolled back on failure) and `main/sync.routes.test.ts → "a database made by the previous build (schema 1)"` (copy + cloud at version 1 → restart → migrated on first use → pushed with no conflict; Sandbox Keep onto an old-shaped cloud). Known corner: the read-only pre-sync file (no local copy AND cloud unreachable at startup) cannot be migrated, so its reads fail until the cloud is back. **Rolling the app back after a migration** (an older `app.asar.<v>.bak`) hits the schema gate: the old bundle shows "Update needed" and refuses to write.
- **libsql close quirk (Windows).** libsql 0.5.x finalises prepared statements only when GC collects them, and the file handle stays open until then — so `close()` right before deleting/overwriting the file (Sandbox discard/keep) hit EBUSY. `backends/libsql.ts` runs a full GC (`v8.setFlagsFromString("--expose-gc")` + `vm.runInNewContext("gc")`), waits one macrotask (the finalisers run there — measured 20/20 vs 0/20 without the tick), closes, then does ONE MORE GC + tick with the reference dropped (the native Database object — and a replica's replicator, which holds the file too — lives until its JS wrapper is finalised); `main/sandbox.ts` and `main/sync.ts → removeReplicaFiles` keep retry loops (the latter with a GC per retry) as the safety net. The backend uses `.all()` for every statement (`.run()`/`.get()` leave a statement half-stepped). A PRAGMA that throws during open closes the half-built handle before rethrowing — a leaked handle keeps the file (and the cloud connection) open with no way to close it.
- **What still uses Prisma:** `prisma/schema.prisma` (source of truth) + `prisma db push` for dev.db; `prisma migrate diff` inside `scripts/generate-schema-sql.ts` and `schema.test.ts`; the generated client only in `prisma/seed.ts` and `scripts/balance-bills.cjs`. The app, the hosted server, the demo server and the tests no longer load `@prisma/client`. `electron-builder.yml` still packages the query-engine DLL — harmless dead weight (`release.yml` is gone since Oct 30 2026). `libsql` is in `dependencies`, so nextron externalises it and electron-builder ships it with its prebuilt `@libsql/win32-x64-msvc` binary; `npm run deploy:prod` checks that binary is byte-identical to the installed one before every swap.
- **`transfer.ts`** (Phase B): `dumpDatabase(exec)` / `loadDatabase(exec, dump)` move every table's rows between any two executors, values verbatim (no coerce), tables parents-first from the `REFERENCES` clauses in schema.sql (`tablesInFkOrder`), the DDL made idempotent (`IF NOT EXISTS`, `INSERT OR IGNORE` stamp) so a load works on an empty file, an empty cloud database, or a populated one; `loadStatements(dump)` is the same thing as `{ sql, args }` batches for `@libsql/client`. Used by the first upload, Sandbox Keep while synced, Import, and backups/exports of a replica (a replica can't `VACUUM INTO`: libsql forwards it to the cloud as an unsupported statement). `schemaVersionGate(v)` is the version check's message.
- **Next: the phone app, `plans/phone-app.md`** (agreed Nov 2 2026, revised Nov 9). The first attempt (Phase C: the whole desktop renderer in Capacitor with a `@capacitor-community/sqlite` backend, branch `android-app`, PR 20) was rejected and deleted. The phone is now a separate phone-native UI in `phone/` that runs this same `DataStore` on a `SqlExecutor` over `@libsql/client/web` — online only, straight to the user's Turso database, read-only except transactions.

## Settings page + app meta (Oct 27 2026)

## Sync (Phase B, Oct 27 2026 — local-first since Oct 29 2026)

Opt-in, bring-your-own cloud database (`plans/phone-app-and-sync.md`): the user creates a free Turso database, pastes its URL + token into Settings → Phone & sync, and the desktop keeps a **local copy** of it that syncs in the background. Guide: the "Sync across devices" step of the picture tour (`docs/index.html#sync`, which Settings' "Step-by-step guide" link opens; its two pictures come from `tour.mjs` against the sync mock).

- **Model (reversed Oct 29 2026).** Phase B shipped libsql's *remote replica* (every write forwarded to the cloud before the API answered; offline = read-only) for "one source of truth, no conflicts". After a day of real use the user overruled it: every save took 1–3 s (more after a quiet spell, because a reachability probe ran before each write), and they want local-database speed with sync in the background. The desktop is now a libsql **synced database** (offline writes): `openLibsql(path, { sync: { syncUrl, authToken, offline: true } })` → `new Database(path, { syncUrl, authToken, offline: true })` (libsql 0.5.29 = Rust libsql 0.9.30 `Builder::new_synced_database`). Every read and write is a plain local WAL operation — measured through the API in `main/sync.routes.test.ts`: median 3.0 ms per write with sync on vs 6.7 ms with sync off in the same run (identical code path; the "off" batch carried the warm-up) — and `sync()` pushes the WAL frames written since the last push, then pulls the frames other devices pushed. Verified against the real client (all pinned by the tests): OPEN needs the network only when `replica.db` + `replica.db-info` (libsql's metadata: `durable_frame_num`, `generation`) are missing — it then bootstraps from the cloud's `/export`; with both present it opens with no network (4 ms). A write never touches the network, even while a sync is stuck. `sync()` resolves `{ frames_synced: 0 }` when the cloud can't be reached (libsql folds the network error into "nothing synced" — that is the offline signal; a pull always reports ≥ 1) and REJECTS with `InvalidPushFrameConflict` / `InvalidPushFrameNoHigh` when the cloud moved on while this file had unpushed frames (`isSyncConflictError`). `PRAGMA busy_timeout` works in this mode (a remote replica rejected it). The local WAL is checkpointed only when the cloud starts a new generation (libsql disables ordinary checkpoints), so it grows between generations. Still true: the sync uses the native addon's `databaseSyncAsync` (tokio, non-blocking; the promise API can't open a synced database in 0.5.29) and now returns libsql's `Replicated` as `SyncResult { framesSynced }`; `.all()` for every statement; the GC + tick before close (the sync context holds the file too).
- **The protocol is Turso-only.** `GET /info`, `GET /export/{generation}`, `POST|GET /sync/{generation}/{start}/{end}` (raw 4120-byte WAL frames; the receiving side ignores salts/checksums and compares page bytes at taken indexes) exist in Turso Cloud, NOT in the open-source `libsql-server` image — Docker cannot verify this mode. `tests/helpers/libsql-sync-server.ts` is a protocol-faithful mock (mirrors libsql's own `sync/test.rs` server plus the second-writer rule: a push that doesn't continue the frame log → `status: "conflict"`) that also speaks Hrana v2 (`/v2/pipeline`, `store_sql`), so the app's REAL `@libsql/client` transport works against it — since Nov 9 2026 including what a BROWSER client needs (the phone app, `plans/phone-app.md`): CORS preflights, and Hrana **streams kept open by a baton** across several HTTP requests (`client.transaction()`, an interactive transaction; a stream holds the mock's one session turn and is rolled back after `STREAM_IDLE_MS`, 10 s, of silence). It runs in a CHILD PROCESS (`libsql-sync-server-child.ts`, `startSyncServerProcess()`): libsql bootstraps inside the synchronous `new Database()` (block_on on the JS thread), so an in-process server deadlocks. If that child dies, every later call now fails at once with its exit code (`SyncServerProcess.exited`, Nov 9 2026): a native libsql crash in the child (Windows access violation, exit code 3221225477) happened in roughly one run in eight while an orphaned `vitest run` was loading the PC — with the old and the new mock alike, and not once in twelve runs on the quiet machine — and before this each remaining test's hooks waited out their full timeout on the dead process, so the run looked hung for minutes. **That crash is gone since Nov 12 2026 (PR 32):** the mock's own databases (the temporary copy each Hrana session runs on, and the empty base file) are opened with Node's built-in `node:sqlite` instead of libsql. It was libsql 0.5.29 itself crashing while tearing a connection down after a session that ran many statements (a schema load) — whichever way the handle was released: `close()` after a GC, `close()` alone, or left to the GC. Schema 3 made the dump one table longer and CI then failed twice in a row; a stress loop over the mock (`reset` + schema load + 3 statements, 400 times, 12 processes at once) crashed 13–15 of 36 processes before and 0 of 36 after, and `sync.routes.test.ts` passed 15 of 15 runs three at a time. The app's side is untouched and still the real libsql client; the frames and file format are plain SQLite's either way. The same teardown exists in `backends/libsql.ts → close()` (Sandbox, sync re-bootstrap) but runs a handful of times per session of use, not thousands. Never leave a stalled `vitest run` behind: stopping the shell does not stop its node processes (`tasklist | grep node`). Standalone for browser checks: `npx tsx tests/helpers/libsql-sync-server-child.ts --port 18081`, then connect to `http://127.0.0.1:18081` with any token. Turso's docs still list `offline: true` as supported; the live run against the user's own Turso database is the one thing the mock can't prove.
- **No write gate.** `main/api-server.ts` calls the synchronous `writeBlockReason()` before POST/PATCH/DELETE: only the schema gate and the read-only corner (below) refuse writes → `409 { error, message, code: "WRITES_BLOCKED" }`. The probe-before-write, `writeBlockReasonNow`, `WRITE_PROBE_MAX_AGE_MS` and the 327 s black-hole concern are gone: a hung cloud can delay no write (pinned: a write answers in < 500 ms while the mock never answers). The only thing a hung sync could hold is the store's lock (a sync takes it so no statement interleaves with a frame insert), so `getStore().sync({ timeoutMs })` gives up after `SYNC_TIMEOUT_MS` (30 s; the native call settles on its own later).
- **`main/sync.ts`** (no Electron imports; circular with `main/sandbox.ts` on purpose, call-time only): `initSync()` (main.ts, before `startServer`: a saved setup opens the copy — no network — and runs one sync, which pushes what the previous run left unpushed), `probeRemote`, `connectSync({ url, token, source? })`, `syncNow`, `resolveConflict("cloud" | "local")`, `disconnectSync`, `exportDatabase`, `importDatabase`, the sandbox hooks `pauseSyncForSandbox` / `resumeSyncAfterSandbox` / `keepSandboxToSync`, `snapshotCurrentDatabase`, `writeBlockReason`, `noteLocalWrite`, `getSyncStatus`. `runSync` = push + pull with the outcome recorded: `offline` (0 frames, a timeout or any non-conflict error), `conflict`, or synced (`pendingChanges` → 0, schema gate re-checked). **It also notices when the pull brought in another device's rows** (Nov 9 2026): `PRAGMA data_version` on the store's connection differs across the sync exactly then (libsql applies pulled frames through a connection of its own; this connection's own commits and a push never move it; libsql's `frames_synced` can't tell — it is ≥ 1 for any sync that reached the cloud) → `state.remoteChanges += 1`. The PRAGMA is read on the BARE connection (`getCurrentConnection().exec`), never through the store: the store's first use runs `prepareDatabase`, which on a freshly bootstrapped copy creates the schema locally and turns the first sync into `InvalidPushFrameConflict` (the tests caught it). A timer syncs every 60 s (`SYNC_INTERVAL_MS`) and 3 s after a route wrote (`noteLocalWrite(count = 1)`, which also counts `pendingChanges` — a batch counts its rows); both `unref`ed. **The 60 s tick stands down while writes are still landing** (`intervalTick`: a write less than `SYNC_AFTER_WRITE_MS` ago → skip; the after-write timer syncs once they stop) — a sync started mid-run holds the store's lock for its round trips, which is what froze the app during Optimize on Nov 6 2026 (see "Overview optimizer"). Test hooks for it: `__setSyncAfterWriteMsForTests`, `__intervalTickForTests`. `pendingChanges` = writes since the last push in this run, seeded after a start from `replica.db-info`'s `durable_frame_num` vs the WAL file's frame count (an estimate). Test hooks: `__setSyncTimeoutForTests`, `__resetSyncForTests({ keepFiles })`, `__setSyncTransportForTests` (unused by the current tests — they run the real transport).
- **States.** `GET /api/sync` → `configured, url, state: local|synced|syncing|offline|paused|blocked|conflict, lastSyncedAt, lastError, syncing, pausedBy, schemaGate, readOnly, writesBlocked, pendingChanges, pendingPush, conflict: { message, since } | null, remoteChanges, replicaPath, appSchemaVersion` (the token is never returned). `remoteChanges` counts, in this run, the syncs that brought in rows this PC did not write; the renderer reloads its data when it rises (see Renderer). `offline` is read-WRITE with the pending count; the next successful sync pushes. **Conflict** = libsql refused the push because another device pushed first; nothing is merged or guessed: writes keep working locally, syncs stop (`POST /api/sync/now` → 409 `SYNC_CONFLICT`) until `POST /api/sync/resolve { keep: "cloud" | "local" }`. `"cloud"` writes this PC's rows (unpushed included) to a `.bak` (`backupFilePath()` naming), deletes the copy and bootstraps it again from the cloud; `"local"` writes the cloud's rows to a `.bak`, replaces the cloud's rows with this PC's (Hrana batches, `replaceRemote`), then bootstraps the copy again so the two agree frame for frame. Both need the cloud (502 otherwise); without a conflict → 409 `NO_CONFLICT`. `readOnly` is now only the corner "no local copy AND cloud unreachable at startup": the pre-sync local file is shown read-only (`writesBlocked` says so) and every tick retries the bootstrap; a bootstrap whose first pull fails is thrown away (the base snapshot may lack the tables, and `prepareDatabase` would create them locally and clash with the cloud). An `InvalidLocalState` open (one of the two files deleted by hand) backs the copy up to a `.bak` and re-bootstraps.
- **Connect / disconnect / sandbox / import.** Connect = validate → probe (409 `SCHEMA_NEWER`; 409 `REMOTE_HAS_DATA` when the cloud holds rows and no `source` was given — the UI asks "use the cloud data on this PC" vs "replace the cloud with this PC's data") → upload the local dump when the cloud is empty or `source: "local"` → delete any old copy → bootstrap the copy + first sync → save settings (any failure after the upload leaves the device local only, 502). Disconnect ("Forget this device") dumps the copy — unpushed changes included — into the local file (`.bak` of the old one first), deletes the copy + `sync.json`; the UI says how many changes never reached the cloud. Sandbox enter dumps the copy into the plain sandbox file (offline OK) and pauses; discard reopens the copy (no network needed); keep writes a `.bak` of this PC's rows (from the closed copy), replaces the cloud's rows with the sandbox's, then re-bootstraps the copy (needs the cloud — 502 and the sandbox stays active otherwise). Import while synced = `.bak` → replace the cloud's rows → re-bootstrap. Export and backups = data-layer dump of the copy (`method: "dump"`), offline OK. A generation change on the cloud (its checkpoint) is followed: libsql checkpoints the local WAL and carries on.

## Key Patterns

### Responsive layout (Oct 2026)
The renderer is plain Next.js with no Electron-only APIs, so the same UI is meant to work in a narrow desktop window and, later, in a phone browser (a future PC ↔ phone sync is planned; the API would then need auth and a configurable address instead of the hard-coded loopback).
- **Sider**: `CustomSider` is a permanent 260px column at `SIDER_BREAKPOINT` (`md`, 900px) and wider, and a temporary `Drawer` below it. `MobileTopBar` (the ThemedLayout `Header` slot) renders the hamburger only below that breakpoint; both share Refine's `useThemedLayoutContext().mobileSiderOpen`. The drawer closes on any route change. Neither uses `noSsr` — it caused a hydration mismatch against the static export.
- **Breakpoints, not device sniffing, for layout**: Overview pay-week cards wrap below `lg` (`flex: 1 1 170px`, surplus card takes its own row), Bills/Personal grids go 3-per-row at `md` and only split evenly across pay weeks at `lg`. The Plan toolbar stacks the Ready-to-Assign pill above the buttons below `md`. The Plan table scrolls sideways at `xs` (`minWidth: 440`). Statistics uses `minHeight: 100%` so a short window scrolls instead of squeezing the chart out (`MonthlyStackedBars` keeps `MIN_CHART_HEIGHT`, with the SVG absolutely positioned so it can't ratchet the measured box).
- **`hover: none`, not width, for touch**: hover-revealed controls (Plan drag handles and row actions, sider account pencil) get `"@media (hover: none)": { opacity: 1 }` so a resized PC window keeps its hover behaviour. `tooltipStyleProps` sets `enterTouchDelay: 0` so a tap opens the shared tooltips. Charts toggle highlight on click as the touch fallback.
- Popovers cap at `min(<px>, calc(100vw - 32px))`; dialogs were already `fullWidth` + `maxWidth`. Number fields carry `inputMode` (`decimal` for amounts, `numeric` for day fields). Viewport heights use `100dvh` with a `100vh` fallback. The Electron window has a 720×480 minimum (`main/main.ts`).
- Demo servers for checking layouts without touching dev.db: `.claude/launch.json` has `demo-api` (port 5858, demo.db) and `demo-ui` (port 8888). While the INSTALLED app is running it owns 5858, so use `demo-api-5859` + `demo-ui-5859` instead: `scripts/demo/serve.ts --port 5859` and `next dev` with `NEXT_PUBLIC_API_URL=http://127.0.0.1:5859/api` (read by `renderer/lib/api-url.ts`; unset in the PROD build, so the installed app always uses 5858). `isAllowedHost` in `main/api-server.ts` checks against the port actually passed to `startServer` (port 0, the route tests, keeps 5858).
- Phone check (Oct 27 2026, S25 Ultra = 412×915 CSS px): every sider page was walked at that size and at a 1000×480 desktop window. Rules that came out of it: every header row that holds a title + button wraps (`flexWrap`) with `whiteSpace: nowrap` on the button, so a label never breaks mid-phrase; the sider column's children carry `flexShrink: 0` (MUI `Collapse` has `min-height: 0`, so the Cash list was the only thing that shrank in a short window and its rows painted over Payees/Expenses); grid columns that hold a fixed-size child use `minmax(0, 1fr)` (the Statistics donut forced its 320px onto the legend); the Overview summary tiles need ~280px each.

### Auto-assign amounts
- `repeatWeekly` Personal items (Gas, Spending, etc.) → **always add a flat per-period amount** (never cumulative top-up). This is intentional — each pay week gets a fresh allowance regardless of prior assigned state.
- `splitAcrossWeeks` Personal items → cumulative top-up. Target = sum of per-period slices (from `computeSplitPersonalAllocations`) through the clicked pay week; caller subtracts current `available` so already-funded prior weeks aren't double-counted.
- Bills with a `BillSplit` row per pay week → cumulative top-up (same shape as split personals). Prevents prior-week funding from masking later weeks' slices when the user hits Auto for P3 expecting P3's share to be added on top.
- Single-week bills (no split, or one `BillSplit` row) → full amount only in the natural pay week (via `getBillPeriodKey` forward-extension logic).

### Multi-occurrence bills (Aug 2026)
A monthly bill can fire **twice** within a single pay-period view — once as the in-month occurrence, once as the next-month forward-extension. Example: a bill with dueDate=4 in Sept 2026 has coord=4 (Sep 4, P1) AND coord=34 (Oct 4, P5).

- `getBillOccurrencesInView(dueDate, periods)` in `pay-period-utils.ts` returns EVERY occurrence in the view (up to 2). Prefer this over `getBillPeriodKey` (which returns only the primary). It never includes the next view's first-week firing — that is a pre-save candidate (`getPreSaveOccurrence`), see "Pre-saving".
- `BillSplit.occurrenceCoord` tags which occurrence a split funds. Legacy rows (`coord=0`) map to the primary (next-month-preferred) occurrence for backward compat until re-optimized.
- `balancePayWeeks` places per-`(billId, occurrenceCoord)` units, so a bill firing twice gets two independent placement decisions (each may be split further).
- **Plan-page mapping invariant:** anywhere splits are read out of Refine and passed into `getBillAllocationsForBill` / `resolveAutoAssignAmountForPeriod` (currently `BudgetPage.tsx handleAutoAssign`, plus `OverviewPage.tsx`, `BillsOverview.tsx`, `CashFlowOverview.tsx`, `PersonalOverview.tsx`), the mapping MUST include `occurrenceCoord: Number(r.occurrenceCoord ?? 0)`. Dropping this field collapses non-primary occurrences into the primary's legacy-fallback bucket and double-counts the secondary firing (secondary gets natural attribution + primary picks up its splits). Regression pinned by `resolveAutoAssignAmountForPeriod — multi-occurrence bills` tests in `budget-utils.test.ts`.
- **Invariant guard:** `assertNoUnderfundedBills(result, context)` throws when any occurrence's `allocations + locked cents < bill.amount`. The Overview optimizer calls this after every month. Occurrences that can only be funded from locked weeks are exempt — they're reported in `BalanceResult.skipped` instead (see "Locked weeks in balancePayWeeks").

### Per-week income overrides (Nov 10 2026)
The user's hours jump between 32 and 40, week by week. An **`IncomeOverride(incomeId, payDate, amount, hours?)`** row (`@@unique([incomeId, payDate])`, cascade-deleted with its income) replaces ONE paycheck of ONE income. No row = `Income.amount`. This replaced the "set the income to the 32 h floor" workaround; the table had been designed in Oct 2026 and not built.
- **Keyed by the payday's DATE, not a week number** — `payDate` is the local calendar date as a YYYYMMDD **Int** (`payDateKey`, Nov 18 2026 → `20261118`). So it changes exactly that pay week, never "every week 3", and it follows the paycheck into whichever view looks at it (a Dec 2 override shows in December's P1 and in November's `nextViewFirstWeek`). An Int, not a "YYYY-MM-DD" string: `transformBody` turns such strings into Dates.
- **One place applies it:** `getIncomePaymentsForPeriod` (per-source amounts + the override applied) and `computeIncomePerPeriodCents(…, overrides)` in `pay-period-utils.ts`. Callers: `planOptimize` (both the month's weeks and the next view's first week; `OptimizeInputs.incomeOverrides`), `CashFlowOverview`, `PersonalOverview`, `BudgetPage`. With no overrides every number is bit-identical to before (the lock-in snapshots did not move). A source still counts once per period; on a bi-weekly grid the first overridden payday inside the period decides. `amount: 0` is valid (an unpaid week); an unreadable amount is ignored. The legacy AppSettings source has no id, so no overrides.
- **`hours` is a label, never math — and the amount is estimated like a pay stub.** `Income.amount` is TAKE-HOME (after taxes and deductions; the form says so). Three optional fields under "When your hours change" in the income form describe the regular paycheck: `baseHours` (the hours `amount` is for), `baseTaxes` (taxes taken out of it — they scale with hours) and `baseFlatDeductions` (union dues — the same every paycheck). Gross is never stored: it is `amount + baseTaxes + baseFlatDeductions`. With `baseHours` set, typing hours in the week's dialog fills the amount through `estimatePaycheck` in **`lib/paycheck-estimate.ts`**: gross and taxes × hours/baseHours, minus the flat deductions as they are — so a 32 h week pays a bit LESS than 80% of a 40 h one (generic example: $800 gross − $80 taxes − $20 dues = $700 at 40 h → $640 − $64 − $20 = $556 at 32 h). The dialog shows that breakdown when taxes or flat deductions are entered; each part is rounded to the cent on its own so it always adds up; 0 hours = $0 and nothing goes negative. The taxes cancel out algebraically (take-home = (amount + flat) × ratio − flat), so they matter only for the breakdown. Taxes are treated as proportional (on the user's stub most of them are flat percentages; only income-tax withholding falls faster), which estimates a short week slightly low — the safe side; the amount stays editable for the real number. None of these fields is a plan input or part of the signature: only the saved override amount is. Pinned by `lib/paycheck-estimate.test.ts`. **The user's real stub numbers must never appear in the repo** — tests and the demo use the generic example.
- **Optimize:** a short week simply has less income in `balancePayWeeks`, so bills move out of it into other UNLOCKED weeks of the same month until the surplus target holds; other months are untouched unless a pre-save links them. A week that has already started is locked: an override there changes its displayed income and surplus, never its bill rows. Removing the override restores the original plan.
- **Signature + triggers:** overrides are folded into the `incomes` signature after a `|` (`…|<incomeId>@<payDate>:<amount>`) and ONLY when there are any, so a baseline saved by an older build still matches and the upgrade starts no re-plan; `hours` is not part of it. `IncomeOverride` is in the automatic runner's `INPUT_RESOURCES`, and `fetchOptimizeInputs` reads it.
- **Pay is a period in arrears (user clarification, Nov 10 2026):** the hours worked Nov 11–17 arrive in the Nov 18 paycheck, which funds pay week "Nov 18 – Nov 24". An override is, and stays, keyed to the PAYDAY (that is the money the plan spends); the work period is display only. `listIncomePaychecks` returns `workStart`/`workEnd` (previous payday … day before this payday), each tile says "Worked Nov 11 – Nov 17" under its pay-week dates, and the dialog reads "Paid Nov 18, for the hours worked Nov 11 – Nov 17" with the fields labelled "Hours worked Nov 11 – Nov 17" / "Paycheck on Nov 18". Never label a tile by its work week alone — it must keep matching the Overview's pay-week cards.
- **UI:** `components/app-settings/sections/IncomePaychecks.tsx` (dialog with the hours, the pay-stub breakdown and the amount), under each income on the Income page: tiles for the pay week covering today and the next ones (`listIncomePaychecks`, 8 at a time, "Show more weeks"), each "NOV · WEEK 3 / Nov 18 – Nov 24 / $560.00 · 32 hrs", amber + CUSTOM when overridden. Clicking one opens the dialog (hours, amount, "Use regular amount" = delete the row). **The current week (NOW) is editable, behind an amber warning in its dialog**: the paycheck is already paid and the week's bills are locked, so the change only moves that week's income and surplus on the Overview — it is for recording what was really paid (user decision, Nov 10 2026; the tile was read-only for a moment the same day, then reopened with the warning). "Show fewer weeks" appears once the list is past its first 8. Saving the regular numbers deletes the row instead of storing a no-op. The Overview's pay-week card shows the hours in amber under the income (absolutely positioned so the cards stay the same height) and in the income tooltip. Past weeks are not listed (their rows stay, so history keeps showing what was paid).
- **Tests:** `renderer/lib/income-overrides.test.ts` (helpers, the paycheck list, `planOptimize` with a short week: fewer bills that week, every bill still funded, Dec/Jan identical, idempotent, removal restores the plan, a started week is left alone; the signature) and the override run in `auto-optimize.test.tsx`. Generic data only ($700 for 40 h).

### Work week (Nov 12 2026)
The user's work week is not their pay week (paid Wednesdays, hours counted in a different seven days). **`Income.workWeekStart`** (Int?, 0 = Sun … 6 = Sat; null = not set) is the weekday the work week starts on. It is **display only**: `listIncomePaychecks` uses it for `workStart`/`workEnd` — the "Worked Nov 8 – Nov 14" line on each paycheck tile and the dialog's labels — and nothing that plans money reads it (not in the signature; saving it starts a run that skips).
- **Rule:** a paycheck is for the last FULL work week that ended before its payday (`workEndFor`: step back from the day before the payday to the weekday before `workWeekStart`); it starts the day after the previous paycheck's work period, so bi-weekly ranges stay gap-free. Not set, or set to the payday's weekday = the old behaviour (previous payday … day before this one). `normalizeWorkWeekStart` exists because `Number(null)` is 0 = Sunday.
- **UI:** "WORK WEEK STARTS ON (OPTIONAL)" in the income form (`IncomesSection.tsx`) — seven weekday toggles, click the selected one again to clear; the line under it spells the week out ("Work week: Sunday – Saturday"). The income's row shows "Works Sun – Sat".
- Pinned by the `workWeekStart` tests in `renderer/lib/income-overrides.test.ts`.

### Orphan-fallback skip
`getBillOccurrencesInView` would orphan-attribute bills that fire before this view's first payday AND past its forward extension — EXCEPT when the NEXT view's first payday is ≤ the bill's dueDate. In that case the next view naturally covers the firing, so orphaning here would double-count the same real-world payment across two views. See `PayPeriod.nextViewFirstPayday`.

### DueDate > daysInMonth clamping
For a bill due the 31st in a 30-day month, `getBillOccurrencesInView` clamps the in-month coord to `daysInMonth` (so coord=30 for Sept, displayed as "the 30th") instead of leaking into the next-month coord range (which would falsely display as "Oct 1st"). Prevents end-of-month edge-case display bugs (bills due the 29th–31st).

### Locked weeks in balancePayWeeks (Oct 2026)
- A week **locks once it STARTS** (`isPayWeekLocked`: `startDay <= todayCoord`), so the **current** week is locked — its paycheck is already handed out. (Was `endDay <= todayCoord`, which let Optimize rewrite the in-progress week's surplus.) Shared by `balancePayWeeks` and the Overview optimizer — never re-inline the rule.
- **Phase 2 leveling never spreads cents into locked weeks** (`splitEligible` = unlocked subset of `eligible`). Leveling a few dollars of a bill into locked P1, which already had a row for that bill, was the Oct 2026 unique-constraint 500.
- **Nothing new is ever placed in a locked week.** An occurrence (or uncommitted remainder) whose eligible weeks are ALL locked — a bill moved/added into the current week, a price bump on a bill due this week, a past firing with no row — is returned in `BalanceResult.skipped` instead: not planned this cycle, exempt from `underfunded`. The user covered it outside the plan (e.g. savings); the next occurrence is planned normally. (User decision, Oct 18 2026 — a bill moved 31st → 18th on the 18th.)
- Skipped occurrences with **no** rows get a **$0 marker row** in their home week, planned by `planOptimize` (written by `handleOptimize`). Without it, `getBillAllocationsForBill` falls back to natural attribution and shows the full amount in the current week anyway (and Plan's ⚠ fires). The marker is a locked row on the next run (`hasLockedRows: true`), so the skip is idempotent. `BillsOverview` renders it dimmed as "Skipped · added after payday".
- `planOptimize` throws in Phase A (before any write) if the algorithm ever emits an allocation into a locked week — that insert is what collided with the committed row in the Oct 2026 500.
- Regression pinned by `Oct 2026 regression — locked weeks are never leveled into` in `pay-period-utils.test.ts`.

### Pre-saving for next month's first pay week (Oct 2026)
A bill that fires in the NEXT view's FIRST pay week has no earlier week in that view to level into: when a month's first payday is the 4th, bills due the 4th–6th all land on that one paycheck (Nov and Dec 2026 showed ~$85 surplus in P1 vs $160–$220 elsewhere). Optimize now saves ahead for them from the current month's unlocked weeks.
- **Attribution is unchanged** — still no backward extension. `getBillOccurrencesInView` never returns the next view's firing; the full-year coverage test still counts every firing in exactly one view. Pre-saving only adds optional `BillSplit` slices in the prior month.
- **Candidate** = `getPreSaveOccurrence(dueDate, periods)`: the bill's day (clamped to the next month) lies in `[nextViewFirstPayday, nextViewFirstWeekEndDay]` (both on `PayPeriod`, with `daysInNextMonth`). Its coord in the prior view is `day + daysInMonth` — the forward-extension convention — which is always PAST the view's last period end (`isPreSaveCoord`). That is how display code recognises a pre-save row; there is no natural fallback for one.
- **Balance**: `balancePayWeeks` takes `nextViewFirstWeek` (that week's income + optimizer personal expenses) and adds it as one VIRTUAL week (index `periods.length`) that only pre-save units may use; this view's own bills never move into it. Phase 2 levels the cluster across the unlocked weeks + the virtual week until no week is over budget. Virtual-week rows are NOT returned (`nextViewFirstWeekBillCents` reports the total) — the next month plans its own first week. Locked weeks still never receive new cents; a pre-save row already in a locked week is committed (`lockedAllocations`) and only the remainder is leveled.
- **Next month** gets `priorViewAllocations` (prior-month rows with `isPreSaveCoord`, re-keyed to its in-month coord by subtracting the prior month's length): committed funding that reduces the occurrence's remainder and counts in `assertNoUnderfundedBills`, but never enters that month's `perWeek` and never counts as a row (`hasLockedRows`). `planOptimize` carries each month's freshly planned rows forward in `effectiveRows` so month M reads M-1's pre-saves from the same run; the fast path and idempotency hold across the pair.
- **Display / Plan**: `getBillAllocationsForBill` returns pre-save rows with `isPreSave: true, isSplit: true` (BillsOverview: "Split · Dec 4th" in November with cumulative Saved) and puts `priorViewSavedCents` on the first row of a first-week occurrence (capped at what its own rows leave uncovered, which neutralises leftover orphan-era rows in locked history). The natural fallback for such an occurrence is the remainder, not a second full amount. `resolveAutoAssignAmountForPeriod` treats either flag as cumulative and adds `priorViewSavedCents`, so in the firing month the P1 target is the FULL bill (the pre-saved cents sit in the same envelope) and the ⚠ badge never reads them as over-funding; BudgetPage's paid-occurrence credit includes them too. All split mappings keep `occurrenceCoord` (see the Plan-page mapping invariant).
- Pinned by the `Pre-saving` describes in `pay-period-utils.test.ts` (helper, balance, locked weeks, prior-view funding, display, `planOptimize` end to end + idempotency) and `budget-utils.test.ts` (Auto-assign / badge agree with the Overview).

### Bill balance schema
`BillSplit(billId, monthKey, weekIndex, amountCents, occurrenceCoord)` with `@@unique([billId, monthKey, weekIndex, occurrenceCoord])` — replaces the old `BillPayWeekOverride` table (removed). `occurrenceCoord` distinguishes multiple firings of the same bill in one view. The `balancePayWeeks` algorithm writes splits to fine-tune per-week amounts.

### Overview optimizer — locked-week semantics
`planOptimize` (`renderer/lib/optimize-plan.ts`) treats every split row in a locked past week as "already committed" (`lockedAllocations`), regardless of whether it matches the algorithm's natural attribution. Only splits in NON-locked weeks get deleted and recomputed on Optimize. Legacy `coord=0` rows are resolved to the primary occurrence via `getBillOccurrencesInView`. Deleting locked history was the bug that caused P3/P4 to inherit the full two split bills amounts and crush the weekly surplus.

A run is two-phase and lives in **`runOptimize` (`renderer/lib/optimize-run.ts`)**, shared by the Overview's button (`handleOptimize`) and the automatic runner (`lib/auto-optimize.tsx`, see "Automatic Optimize") so the two cannot drift: **Phase A = `planOptimize`**, a pure function that plans all 36 months (balance + `assertNoUnderfundedBills`) with zero DB writes, **Phase B applies** deletes → creates (unlocked allocations + $0 skipped markers; `buildBatchOperations`, each month's deletes before its creates) as **ONE `POST /api/batch` request = one transaction** (`lib/batch-api.ts` → `DataStore.batch`, since Nov 6 2026), followed by one `notifyLocalWrite()` + `invalidate("BillSplit")` since the raw request bypasses Refine, then the baseline save (`AppSettings.optimizedInputsSig`, through the caller's Refine `useUpdate`) and the alert clear — success only. `handleOptimize` adds the toast. Until then every row was its own Refine mutation (995 POSTs + the deletes on Nov 6 2026, each its own commit): with sync on, the renderer's post-save sync and the 60 s timer kept starting syncs in the middle of the run, each holding the store's lock for its round trips to Turso, so the remaining writes and every read queued behind the network — the app froze, and the thousands of WAL frames ended in a sync conflict. Measured against the mock: 100 rows = 306 frames as single requests vs 12 as one batch; a real 1818-row re-plan = 47 frames. A planning failure leaves the DB untouched, and so does a failure inside the batch (it rolls back). The old single loop deleted a month's rows and then died mid-create, silently dropping two split bills from Oct 2026. Failures show an error toast and keep the stale alert; success alone clears it. Since Oct 2026 each month is balanced together with the NEXT month's first pay week (see "Pre-saving"), so consecutive months are linked through `effectiveRows`; everything else about a month is still independent.

### Optimize horizon
The Optimize loop runs `OPTIMIZE_HORIZON_MONTHS` (currently **36** = 3 years) forward from today. Bumped up from 12 so users scrolling to future months always see properly-planned `BillSplit` rows instead of raw un-optimized amounts. Iterations are independent (each month reads only its own state), so the cost scales linearly — first run writes ~50 splits/month × 36 months; subsequent runs hit the identical-signature fast-path early-exit and skip untouched months entirely. The constant lives in `lib/optimize-plan.ts`; the success toast reads it. If you change the horizon, update the doc comments and the `36` expectations in the Optimize tests.

### Automatic Optimize (Nov 6 2026)
Optimize runs by itself after any write that changes its inputs; the Overview's alert + button are the fallback for when that run fails (user request, Nov 6 2026 — the button should never need pressing).
- **One runner per window:** `AutoOptimizeProvider` (`renderer/lib/auto-optimize.tsx`), mounted once in `app/providers.tsx` inside Refine, `SandboxProvider` and `SyncStatusProvider`. `withAutoOptimizeTriggers` wraps the data provider beside `withSyncWriteNotices`: after a successful create/update/delete on **Bill, Personal, Income, IncomeOverride or AppSettings** (`isOptimizeInputWrite`) it calls `notifyInputWrite()`, and the runner schedules ONE run `AUTO_OPTIMIZE_DEBOUNCE_MS` (1 s) after the last such write. **Never on `BillSplit` writes, nor on an AppSettings save whose only key is `optimizedInputsSig`** (the baseline a run saves at the end, and the Overview's first-run adoption) — or the runner would loop on its own output. A write that lands mid-run queues exactly one more run. `useAutoOptimize()` (`lib/auto-optimize-context.ts`, no Refine import) exposes `pending / running / busy`; idle outside the provider, so the lock-in tests see no change.
- **A run** fetches Bill, Personal, Income, IncomeOverride, BillSplit and AppSettings/global fresh from the API (`fetchOptimizeInputs`; the Refine caches may be stale), computes `computeInputSignatures` (the Overview's rule, now in `lib/optimize-run.ts`), **skips when they equal the saved baseline** (a write-triggered skip also clears a stale failure alert), otherwise calls the shared `runOptimize` with `today = new Date()`. No primary income → nothing to plan. The planner's fast path makes a no-op run cheap (five GETs, no batch; the baseline is still saved when the signatures differ).
- **Start-up check** (`AUTO_OPTIMIZE_STARTUP_DELAY_MS`, 1.5 s after mount): runs when the baseline differs from the inputs (an edit whose run could not finish, or made in another window) OR when the horizon's last month (`today + OPTIMIZE_HORIZON_MONTHS - 1`) has no `BillSplit` rows while there are bills — so the farthest month out does not stay unplanned until the next edit.
- **Failure never fails the user's save:** it is logged and written to the Overview's alert as `"Automatic re-plan failed: <message>"` (`AUTO_OPTIMIZE_FAILED_PREFIX`, `writeOptimizeAlert` → `localStorage("overviewOptimizeAlert")` + a window event a mounted Overview subscribes to), so the amber alert + "Optimize Now" button appear as the retry (the alert's sub-line says the automatic run could not finish). The Overview never overwrites that text with its generic "were added or updated", and holds its input-change alert back while the runner is `busy` (no one-second flash). A successful run — automatic or manual — clears it, as does a write that leaves nothing to re-plan.
- **Sandbox:** the runner starts no run while a sandbox action is in flight (`useSandbox().busy`) or once `pagehide`/`beforeunload` fired, so inputs read from one file are never written into the other; the reload drops the timer and the start-up check plans whatever the new file needs. Inside an active sandbox a run writes to the copy — correct.
- **Tests:** `renderer/lib/auto-optimize.test.tsx` (fetch, planner, batch and Refine hooks mocked): the trigger rule, one debounced run per burst with the exact batch shape and baseline save, the skip, the queued re-run, the failure paths (batch, planner, API down) writing the alert without throwing, the start-up rules, the unload drop. The Optimize lock-in tests are unchanged and still pin the button's writes.

### Stale-data alert + Optimize button (Overview) — the fallback
- Fires when bills / income / personals / surplus target differ from the **baseline saved by the last successful Optimize** (`AppSettings.optimizedInputsSig`, JSON; `describeInputChange` in `lib/optimize-run.ts`), OR when every `BillSplit` row still has `occurrenceCoord=0` (schema migration signal), OR when an automatic run failed (its message IS the alert). Since Nov 6 2026 the automatic run normally makes the inputs match again within ~1 s, so in day-to-day use the alert shows only after a failed automatic run; the check stays as the safety net.

- Alert text persisted in `localStorage("overviewOptimizeAlert")` — survives navigation and app restarts.
- Cleared only by a **successful** Optimize, which also rewrites the baseline. Triggers `balancePayWeeks` + `assertNoUnderfundedBills`, writes `BillSplit` records with proper `occurrenceCoord`.

### Plan page out-of-sync badge + Sync Plan button
- Amber ⚠ (`WarningAmberIcon`, `#fbbf24`) appears next to a Bill envelope's name in `BudgetItemRow` when funded ≠ expected-through-current-pay-week (fires OVER **and** UNDER; zero tolerance since funding is integer cents throughout).
- For BILL items the tooltip surfaces "still-to-save" numbers, not month-aggregates — subtracts already-consumed grace-window activity from both `expected` and `funded`. Same diff, more intuitive values. (Example: a bill firing Sep 4 and Oct 4 in the Sept view — once the Sep 4 firing is paid, the tooltip shows only the Oct 4 slice still to save through the current week, instead of month totals that include the paid firing.)
- **Paid occurrence = settled** — `activityInBillGraceWindowCents` credits each grace window that has ANY net outflow with that occurrence's full PLANNED amount (sum of its `BillSplit` rows via `getBillAllocationsForBill`, or `bill.amount` if unsplit), regardless of the actual charge. Overpay (charged a little more than the plan) doesn't eat into another firing's "still-to-save" target; underpay (planned $X in a locked past week, charged slightly less) doesn't leave a phantom under-fund that re-optimizing can't fix. Leftover change sitting in the envelope flags as OVER-funded — the right nudge to move it. Unpaid windows (0) and refunds (negative) pass through unchanged.
- **Shared evaluator** — badge (`BudgetItemRow`) and Sync Plan button (`BudgetPage.syncPlan`) both call `evaluatePlanSync` in `budget-utils.ts`, so they can never disagree. Don't re-inline the math.
- **Payday gating (paycheck-driven, not calendar-driven)**: `paydayPending` = today's pay week has started but no paycheck is recorded for it. A paycheck = uncategorized inflow with memo **"Income"** (case/whitespace-insensitive), dated from `PAYCHECK_EARLY_DAYS` (2) before the week's start through today (`hasPaycheckForPeriod`). Memo is the signal because "Transfer from Savings" / balance adjustments are also uncategorized inflows. While pending, under-fund is judged only against the PREVIOUS week's target (real drift still warns); once the paycheck lands the badge compares against the current week. Over-fund always compares against current. Replaced the old "previous week met → silence" heuristic.
- **Sync Plan button** (amber outlined, `AutoFixHighIcon`) sits on the left of the top row (mirroring "Add Group" on the right, RTA pill centered). Only counts **over-funding + drift** (short of EARLIER weeks' targets) — a shortfall that exists only because this week's slice isn't assigned yet is Auto-assign's job and never shows the button, even after the paycheck is recorded. Drift fills to the previous-week target; over pulls back to the current target. Disabled when `readyToAssign + overTotalCents < underTotalCents` — tooltip explains the shortfall.
- **Personal envelopes excluded** — repeatWeekly items (Gas, Spending) fluctuate too much week-to-week to flag meaningfully.

Envelope empty → in sync; money still in it → over-funded, and Sync Plan hands it back.
- **UI:** a MoneyOff icon button beside a BILL envelope's name in `BudgetItemRow` (hover-revealed like the row actions; always visible and teal `NO_CHARGE_COLOR` while a payment in the view is marked). It opens a small menu with one tick row per payment of the bill in this view ("Due Nov 20"; two rows when the bill fires twice). `BudgetPage.handleToggleNotCharged` creates / deletes the row; `BudgetItem.billPayments` carries the view's payments. Not to be confused with the optimizer's "skipped" occurrences (`BalanceResult.skipped`, the $0 marker rows).
- **Known corner:** a pre-save slice saved in the PREVIOUS month for a not-charged first-week payment is still expected in that earlier month's Plan (pre-save rows have no grace window there).
- Pinned by the `creditBillOccurrenceCents` / "marked not charged" tests in `budget-utils.test.ts` (generic $15 "Game pass") and the version-2 migration tests.

### Shared tooltip styles (`renderer/lib/tooltip-styles.tsx`)
Every hover tooltip across the app pulls its shell from `tooltipStyleProps(borderColor)` — dark navy bg, thin colored border + arrow, 150 ms Fade transition. Border color ties the tooltip to its context: **amber (`TOOLTIP_AMBER`)** for warning surfaces (Out-of-sync badge, Sync Plan button), **pay-period color** for card-owned tooltips (BillsOverview split badge, CashFlowOverview income/expenses breakdown). Content typography via `<TooltipTitle color={...}>` (bold accent-colored) + `<TooltipBody>` (0.85 white). Key invariants covered by `pay-period-utils.test.ts`:
- **Full-year coverage** — for every bill in the user's actual bill set, every real-world firing (Aug 2026 → Jul 2027) is attributed to exactly one view. Guards against orphan double-counting AND dropped bills.
- **Multi-occurrence bills** — Sept 2026 dueDate=5 returns 2 occurrences; balance places both; underfunded stays empty.
- **Locked-allocation preservation** — a bill with half its amount locked in P2 has only the remaining half placed in unlocked weeks (not the full amount again).
- **Assertion helper** — `assertNoUnderfundedBills` throws on any short-funded occurrence; the Overview optimizer calls it after every month's balance.
- **Oct 2026 regression (modeled on real data, anonymized)** — locked weeks (incl. the current, started week) never receive new cents; the exact 500 setup emits nothing into locked P1; a bill moved into the current week (31st → 18th) or a price bump there lands in `skipped`; the $0 marker makes the skip idempotent; the next month plans it normally.
- **Pre-saving (generic $325 cluster due the 4th–6th, Oct → Nov 2026)** — Oct's open week saves ahead for Nov P1, each firing is funded exactly once across the two views, locked weeks stay untouched, the next view plans only the remainder, `planOptimize` is idempotent once applied.

Key invariants covered by `budget-utils.test.ts`:
- **Plan ↔ Overview alignment (multi-occurrence)** — `resolveAutoAssignAmountForPeriod` returns the correct cumulative envelope amount when splits carry proper `occurrenceCoord`. Regression guard for the BudgetPage mapping — if occurrenceCoord is ever stripped upstream, cumulative totals inflate (e.g. P5 → 3× instead of 2× the bill on the multi-occurrence case).
- **Plan ↔ Overview alignment (pre-saving)** — the prior month's Auto-assign targets its pre-save slice in the week it was saved; in the firing month the P1 target is the full bill (pre-saved cents included) and `evaluatePlanSync` neither flags them as over-funding nor asks Sync Plan to pull them back.
